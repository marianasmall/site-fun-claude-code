P1 · Subagent-driven builds Tried

The two-step for big builds

For anything big (several files, lots of decisions, more than 30 minutes of work), don't just ask for the thing. Ask for a plan first. Then a team of fresh helper Claudes ("sub-agents") builds it, while the smartest one directs and checks the work. You get fewer mistakes without having to catch them yourself.

Added Aug 7, 2026Paste-and-go
⏱ 2 min

Because: one Claude that builds and checks its own work will miss its own mistakes. A plan plus a reviewer that never saw the work won't.

Paste this into your next Claude Code session

For any substantial build, use this two-step instead of just asking for the thing:

Write an implementation plan, then execute it subagent-driven.

Prerequisite: the superpowers plugin, a free add-on pack that teaches Claude this way of working. Don't have it? Just ask: "install the superpowers plugin". Claude handles it.

Tried it on a build? Tick it off.

What you'll see
> Write an implementation plan, then execute it subagent-driven. ⠋ Planning… 12 tasks mapped → Task 1 · fresh sub-agent builds & self-reviews → reviewer agent (never saw the work) checks it ✓ Task 1 approved · dispatching Task 2

What it does: Claude first writes a detailed implementation plan (every task with exact files, values, and test steps), then executes it by dispatching a fresh sub-agent per task. Each one gets a written brief, builds, and self-reviews; then a separate reviewer that never saw the work happen tries to poke holes in it before the next task starts. The main session only coordinates; it never writes or reviews the code itself. Fresh eyes catch what the author can't.

Why it saves money too: the smartest model does the planning and checking, while cheaper, faster agents do the labor. Best of both.

Make it your standing default

Never remember the phrase again

Tell Claude Code:

Make this the standing default for big builds: add it to my CLAUDE.md.

Claude adds the rule to your CLAUDE.md (the memory file where Claude keeps your standing instructions), and every future build big enough to qualify uses the two-step automatically. You can always opt out per build ("quick and dirty, inline").

P3 · Turn work into skills Tried

Never explain the same job twice

Done the same kind of task with Claude two or three times? Don't keep re-explaining it. A skill is a saved procedure Claude keeps on file and pulls out whenever the job comes up, and Claude can write it for you from work you just finished.

Added Aug 7, 2026Paste-and-go
⏱ 2 min

Because: every time you re-explain a job, you pay for the same lesson again.

Right after finishing a job you'll do again, paste this

While the work is still fresh in the conversation:

Turn what we just did into a reusable skill: capture the steps, the checks, and the gotchas we hit, so next time I can just ask for it by name.

Saved your first skill? Tick it off.

What you'll see
> That report we just built: turn it into a skill. ⠋ Writing skill… ✓ Created ~/.claude/skills/monthly-report/   Next month: "run the monthly report" Claude already knows every step.

The ladder: a prompt you repeat word-for-word becomes a slash command (Fun 07). A whole procedure you repeat, with steps, checks, and judgment calls, becomes a skill. Claude uses it automatically when the job matches, or you call it by name.

How to know it's skill-worthy: you've done it two or three times, it has steps you'd forget, and you keep correcting Claude the same way each time. That correction is exactly what belongs in the skill.

What a skill looks like inside

Just a folder with instructions

A skill lives at ~/.claude/skills/[name]/SKILL.md, written in plain markdown:

---
name: monthly-report
description: Build the monthly client report from the analytics exports
---

1. Ask which month we're reporting on
2. Pull the exports from the reports folder
3. Follow last month's structure: sections, tone, charts
4. Flag any metric that moved more than 20% before writing
5. Save the draft as Report_[Month]_[Year].md and open it

You never have to write this by hand; that's what the paste prompt above is for. Claude drafts it from the work you just did together; you just approve it.

P4 · The memory file Tried

Teach Claude how you work, once

Claude forgets everything between sessions, unless you give it a memory file. CLAUDE.md holds your standing instructions: how technical you are, what to always do, what to never do. Write it once; every session starts already knowing you.

Added Aug 7, 2026Paste-and-go
⏱ 10 min

Because: without it, every session starts with you explaining who you are. Again.

Let Claude interview you

Paste this into Claude Code and answer its questions:

Create a CLAUDE.md for me: interview me about how I like to work (my role, how technical I am, what you should always do, and what you should never do), then write the file and tell me how to change it later.

The file lives at ~/.claude/CLAUDE.md (applies everywhere) or inside a project folder (applies just there). It's plain text: read it, edit it, delete lines that stop being true.

Got your memory file? Tick it off.

Before and after
// without a memory file > Please explain simply, I'm not a coder… (again)   // with one ✓ CLAUDE.md loaded · 24 standing instructions Plain language, backups before edits. Let's go.

The compounding trick: whenever you correct Claude the same way twice, say "add that to my CLAUDE.md." The file gets smarter every week; your sessions stop starting from zero.

What actually belongs in it

Four kinds of lines earn their place

  • Who you are: "Marketing exec, not a coder. Explain what things accomplish, not the syntax."
  • Standing rules: "Always back up a file before overwriting it." "Explain before acting."
  • Preferences: output format, tone, how much detail you want.
  • Corrections that keep recurring: anything you've typed twice belongs here, not in chat.

Want a filled-in starting shape instead of a blank page? The starter kit ships a CLAUDE.md.template. And the "standing default" upgrade in P1 is exactly this: one line in your memory file.

P5 · Resumable projects Tried

Every project resumable from cold

The thread dies, the week ends, and you're back to re-explaining everything. Five small files fix that: any future session picks the project up cold, no re-briefing.

Added Aug 7, 2026In the starter kit
⏱ 5 min

Because: sessions end mid-thought, and re-briefing a project is the part nobody has patience for.

Paste this at the start of any real project

No installs needed. Claude sets up the files and the habit:

Set up this project so any future session can pick it up cold: create README.md, PLANNING.md, and CONTEXT-SUMMARY.md with sensible contents for what we're doing, and from now on end every session by updating a handoff.md I can paste into a new thread: current state, what to read first, next action, and traps to avoid.

The payoff moment: next time a session ends (or dies), you open handoff.md, copy the bottom half, paste it into a fresh thread, and Claude continues like nothing happened.

Project set up? Tick it off.

What you'll see
> /kit:scaffold-project ✓ README · PLANNING · CONTEXT-SUMMARY   …a week later, new thread: > [paste handoff.md] picks up exactly where you left off

Why five files, and what each one does

Each file answers one question

  • README.md: what is this? (for humans)
  • PLANNING.md: where is it going? (goals, roadmap)
  • CONTEXT-SUMMARY.md: what's true right now? (updated each session)
  • CLAUDE.md: project-specific rules for Claude (only if needed)
  • handoff.md: where did we leave off? (replaced every session)

The handoff's Traps line is the sleeper hit: dead ends already tried, decisions already made. A new thread that knows the traps doesn't waste your evening re-hitting them.

P7 · Past sessions Tried

Your old conversations aren't gone

Every Claude Code session is saved as a file on your own machine, for 30 days by default, longer if you say so. Which means Claude can go back and read them: what you decided, what you tried, what that command was.

⏱ 2 min

Because: the answer to "what did we decide?" is usually already sitting on your machine.

Just ask Claude to go look

Paste this with your topic:

Search my past Claude Code sessions for [TOPIC] and summarize what we did and what we decided.

Keep them longer: 30 days is the default, not the limit. One line in ~/.claude/settings.json:

{ "cleanupPeriodDays": 120 }

Found something old? Tick it off.

What you'll see
> When did we set up the sound hooks, and how? ⠋ Reading past sessions… ✓ Found it · July 9: you picked "Glass", wired through notify-done.sh. Want the details?

Sessions are just files

Every conversation lands in ~/.claude/projects/ as a transcript file. Nothing leaves your machine. That's why Claude can read them and why the retention setting is yours to control.

P8 · Parallel sessions Tried

Run several Claudes as a team

Two or three sessions at once (one building, one researching, one on a different project) without chaos. The trick isn't the tabs; it's giving sessions shared places to read and write, so they work like colleagues instead of strangers.

Added Aug 7, 2026In the starter kit
⏱ 10 min

Because: one session at a time means waiting, and several with no shared notes means chaos.

Ask Claude to design your setup

Paste this into any session:

I want to run multiple Claude Code sessions in parallel without them stepping on each other. Set me up: what files should they share, how does one session hand work to another, and what habits keep them coordinated?

Running two at once? Tick it off.

What you'll see
▸ 📊 q3-report  ▸ 🔧 site-fix  ▸ 🧾 invoices   site-fix wrote its handoff → invoices reads it Colleagues, not clones.

The three rules that make it work: shared files beat memory (sessions coordinate through what's written down, not what anyone "remembers") · update the handoff when state changes, not just at the end · when work moves to a new session, the old one writes the new one's first message.

Already installed the starter kit? You have the pieces: self-naming tabs (P2) so you can tell sessions apart, /kit:handoff and /kit:session-end for the baton-passing, and the full primer in the kit's docs/.

Going deeper: same repo, two sessions

Worktrees: parallel work with no collisions

Two sessions editing the same project will fight. Git worktrees give each session its own copy of the repo on its own branch: same history, separate desks. Ask Claude: "set up a worktree so I can work on [thing] in a second session without touching this one."

P12 · Long sessions Tried

Four habits for long days

Claude gets slower, and hits your usage limit sooner, the longer one conversation runs. Nothing is broken. Claude re-reads the whole conversation every time you send a message, so a long one gets heavy. Four small habits fix most of it. Each takes a few seconds, and none of them needs any technical knowledge.

Added Oct 10, 2026Paste-and-go
⏱ 5 min

Because: a conversation that has run all day carries everything you said since morning, and you pay for it on every message.

Four habits, each one a single command

Anything that starts with a slash is just something you type into Claude Code and press enter. It isn't code, and there's nothing to install. You don't need all four habits at once; pick the one that matches your day.

  1. Starting something unrelated? Type /clear. It begins a fresh conversation. Without it, the invoice you finished is still in the conversation while you ask about a press release, and Claude keeps re-reading it all afternoon. If you'll want the old conversation back, type /rename first to name it, then clear. Reopen it later with /resume.
  2. Sitting down for a long session? Type /context. It shows what's already in the conversation before you've typed a word, and how much room each thing takes. Every connected tool (Gmail, Drive, a spreadsheet app) describes itself at the start of every message, whether you use it that day or not. Type /mcp to switch off the ones you don't need. (MCP is just the name for those connections.)
  3. Pick your model at the start, then leave it alone. Switching with /model halfway through makes the next reply slower, because the new model has to read everything from the beginning. Turning on fast mode mid-session does the same. Bigger isn't automatically better: a smaller model is quicker and handles precise, well-described or mechanical jobs well. Keep the biggest for work that's genuinely hard or vague.
  4. Tidy up before you walk away, not after you come back. On a Claude subscription, Claude keeps your conversation quick to reload for about an hour. Heading into a meeting, or stopping for the day? Tell Claude what to keep and compact first:
/compact keep the decisions we made, the files we changed, and the open questions

That swaps the long conversation for a short summary that keeps what you named. Do it an hour later and Claude pays full price for one last complete read first.

Tried one of the four? Tick it off.

What you'll see
> /context Conversation ▮▮▮▮▮▮▮▮▯▯ Connected tools ▮▮▮▯▯▯▯▯▯▯   > /compact keep the decisions and open questions ✓ Conversation summarized

Claude has no memory between messages

Picture a folder of notes on a desk. Every time you send a message, Claude is handed the whole folder and reads it from page one: its own instructions, every document it has opened, everything you've both said. Only then does it reach your new message at the very end. Ask forty questions in one sitting and on the fortieth it's re-reading the previous thirty-nine.

One thing helps. Pages at the front of the folder that are exactly the same as last time get skimmed, which is much quicker. But change something near the front and Claude has to read properly again from that point on. The four habits are all ways of keeping the folder thin, or keeping the front of it still.

If you're on a subscription, "cheaper" means "you get further before Claude makes you stop." Plans have a usage window. Work hard for long enough and Claude tells you to wait. These habits push that point back. The skimmed copy expires if you step away for a while, so the first message after a long break is the slow, expensive one.

Why /clear beats /compact for a fresh start: compacting has to read the whole conversation to summarize it, so it isn't free. Clearing is. Use /compact when you want to keep the thread, and /clear when you don't.

Three smaller ones

  • Tell Claude which file you mean. "Fix the pricing in the September deck" sends it hunting. Type @ and pick the file instead, and the hunt is skipped.
  • Heading the wrong way? Type /rewind. It tears out the last few turns and takes you back to an earlier point. Unlike compacting, it keeps what came before intact, so it costs almost nothing. Better than arguing with it.
  • Push messy jobs to a sub-agent. A sub-agent is a second Claude working in its own separate conversation. It reads the messy thing (a full meeting transcript, a long list of files) and comes back with just the answer. Say "do that in a sub-agent."

When Claude gives you something wrong

Ask which kind of wrong it was, because the fix differs. If it didn't know enough (went the wrong way, missed how things fit together), move up to a bigger model with /model. If it didn't try hard enough (skipped a file, stopped halfway, went shallow), raise its effort with /effort. It works the other way too: if Claude writes an essay when you asked it to change one word, turn the effort down.

Write the instruction once

Tell Claude what to keep every time it compacts

Claude also compacts on its own when a conversation gets full. Paste this so it knows what matters when that happens:

Add a "Compact instructions" section to my CLAUDE.md that tells you what to keep when a conversation is compacted: the decisions we made, the files we changed, anything waiting on me, and my standing rules.

CLAUDE.md is the memory file from P4. The new section takes effect in your next conversation.

Make it yours: this is how one person runs it. Tell Claude which of these habits you want, and it will set them up to suit how you work.

P13 · Meeting recordings Tried

Ask Claude about your meetings

A recording nobody listens to is just storage. Connect your voice recorder or meeting notes app to Claude and it can search and read every recording. Ask what you promised someone, which meetings mentioned the budget, or for a draft follow-up to Tuesday's meeting, and get the answer instead of a replay. Setup is about five minutes.

Added Oct 10, 2026Paste-and-go
⏱ 5 min

Because: the decisions are in the recordings, and nobody has time to listen back.

Connect your recorder, then ask

  1. Check the recorder is signed in to your own account, with cloud sync on. Recordings land in whichever account the device is paired to, and Claude reads the cloud copy, not the device. If you inherited a device from someone else, they need to unpair it first.
  2. In claude.ai, open the left sidebar and go to Customize > Connectors. Search for your meeting recorder or note-taking app. If it's listed, click Connect and sign in with the account from step 1.
  3. Verify it. This step isn't optional. Paste this:
List my recent recordings, with the date and title of each.

Then ask: "Summarize the newest one and list the action items." If you see your latest recordings, you're set. If the list is empty, the device is paired to a different account, or its cloud sync is off.

  1. Make the habit that pays off. While you record, say instructions out loud with a fixed prefix, like "for the bots: remind me to send the deck." Later, ask Claude to find everything you said for the bots in the last few days. Those lines are short and explicit, so they're easy to miss in a long transcript and easy to find by the phrase.

Then ask the questions you actually have: "What did I promise in my last call with a client?" or "Which recordings mention the budget?"

Each person connects their own account. Connectors are switched on per account, and everyone signs in with their own login. On Team and Enterprise plans, an admin may need to switch a connector on before members can connect it. Not every recorder has a connector. If yours isn't in the list, this tip won't work yet.

Got an answer from a recording? Tick it off.

What you'll see
> what did we decide about the launch date? ⠋ Searching recordings… ✓ Found it · Tuesday's team call: moved to the 14th, Sam confirms the vendor by Friday.

What it can do: find recordings by name, keyword, or date; read the full transcript; read the app's own summary and action items. It reads. It can't delete or change anything.

One honest caveat: what Claude reads is the recorder's cleaned-up version of the transcript. It's good for summaries and action items, not for quoting someone word for word. Names and unusual words often come out wrong, especially in noisy rooms. Check any name before you put it in an email, and listen to the original when exact words matter.

Think about what gets recorded. A recorder that's always on picks up everything, including calls you wouldn't want anywhere else. Connect only the account you're comfortable with Claude reading.

It works in Claude Code too

Nothing extra to install

The connection follows your Claude account. It works in the desktop app, on your phone, and in Claude Code. In Claude Code, /mcp shows your connected tools once they've carried over. Not sure which connectors are worth adding? The kit's plugins and connectors primer walks through it.

Make it yours: this is one way to run it. Treat it as a starting point and tell Claude what to change, like which phrase you use or what you want pulled out of each meeting.

P14 · Morning brief Tried

A morning brief waiting for you

Your schedule in order, the three things that matter, and the emails that need a reply from a real person. One short read instead of five tabs. Set it up once, then ask for it, or have it run on its own.

Added Oct 10, 2026Paste-and-go
⏱ 10 min

Because: piecing your day together from a calendar and an inbox is a chore, and Claude is good at chores.

Connect your calendar and inbox, then paste

  1. Connect Google Calendar and Gmail. In claude.ai, that's Customize > Connectors. In Claude Code, type /mcp. You sign in once in a browser window and approve access.
  2. Paste this:
Check my calendar for today and give me a short morning brief: 1) My schedule for today, in order, with times. 2) My top 3 priorities, pulled from my calendar and from anything urgent in my unread email. 3) Emails that need a reply: only messages from real people I know or work with, not newsletters or automated notices. Keep it short enough to read in under a minute. Read only: don't send or change anything.

A good first brief names real meetings and real senders. If it's vague, say so. If it misses an email you'd expect, tell it what to always include, like "anything from my accountant." Claude will use that next time.

Got your first brief? Tick it off.

What you'll see
9:00 Team check-in · 10:30 Vendor call · 2:00 Review Top 3: 1. Send the revised quote 2. Prep for the vendor call 3. Approve the draft Needs a reply: Dana (contract question)

Why it works: the brief isn't clever. It saves the few minutes you'd spend hopping between your calendar and inbox before you start. Because it only reads, there's nothing to undo.

If you travel, say which time zone to use. If you keep work and personal calendars apart, say which ones to check. Claude reads your main calendar unless you tell it otherwise.

Make it a habit

Three ways, from most hands-on to least

  • Keep it manual. Each morning, say "run my morning brief."
  • Make it a command. Ask Claude to save the prompt as a slash command called /morning-brief, then type that each morning. See Fun 07.
  • Schedule it. Ask Claude to set it up to run every weekday morning with the /schedule command. It then runs without you opening anything.

Want it somewhere you'll actually see it? Ask Claude to put each brief in a draft email to yourself instead of the chat.

P15 · Next actions Tried

Put what's left on your calendar, not in the chat

Most work sessions end with something only you can do: a login only you have, an email to send, an approval, a screen Claude can't click. Claude writes it in a tidy summary, the chat scrolls away, and it's gone. Tell Claude to put it on your calendar instead, with the exact links, folders and logins you'll need, so you can act on it from your phone without opening your laptop. Works in claude.ai and in Claude Code. Setup is about five minutes.

Added Oct 10, 2026Paste-and-go
⏱ 5 min

Because: a chat only helps if you remember to go back and look. A calendar comes and finds you.

Add one standing rule

What you get: events created as the work happens, not written down afterwards. Each one carries the real locations: file paths, which folder, which project, the web links, and which account to sign in as. Where a login is needed, it says where the password lives, never the password itself. And for work you'll carry on later, there's a block you can copy on your phone and paste into a fresh Claude chat to restart exactly where you left off. A half-finished job becomes one copy and paste away from restarting instead of a re-explanation.

The modes, in plain terms

Shift+Tab cycles between them

  • Auto: Claude runs routine actions itself and checks with you before risky ones. The default for everyone since Claude Code 2.1.284.

Never let Claude do anything you can't undo

The rule that makes it safe to hand Claude real work: nothing destructive, ever. Files get moved to a review folder instead of deleted. Emails get drafted, never sent. Originals get backed up before overwrites. You keep the only delete key.

P11 · Scoped texts Tried

Give Claude your work texts (and nothing else)

"Let AI read my texts" has always meant all of them: family, doctors, everything. That's the wrong trade, so nobody makes it. The fix: a group in your Mac's Contacts app becomes the permission. Whoever is in the group is visible to Claude; everyone else doesn't exist. A bigger project: save it for when you're comfortable.

Added Aug 19, 2026In the starter kit
⏱ 30 min

Because: your work threads are useful to Claude, and the rest of your texts are none of its business.

A contacts list becomes the permission

First, put your work contacts in one place: a list in the Mac's Contacts app (File > New List; Apple's how-to; older Macs call it a group), or a label in your work Google contacts. Contacts shows iCloud and Google side by side, so either works. Then paste this into Claude Code:

Build an iMessage reader. Derive the allowlist from my [list/label name] contacts, and build it so it cannot return anything outside that list. It may draft replies by opening Messages prefilled, but no send capability may exist in the code. Work from a copy of the message database; the live one is locked while Messages is open. Include a self-test.

Expect one Mac permission step along the way (Full Disk Access for your terminal app); the guide walks you through it.

Then verify. This step is not optional: ask for a work thread (it should come back), then ask for a real personal contact (it should come back empty). Have it draft to a fake number to prove nothing can deliver. A test only proves what it was written to prove, so use a real personal contact, not a made-up one.

Built and verified? Tick it off.

What you'll see
> find the text where the delivery date was confirmed ✓ Searching 26 work threads (of 3,425 on this Mac)   personal messages: in data the tool never opens

The Mac can't scope this for you

macOS permission for reading Messages is all or nothing; there's no OS setting for "work texts only." The scoping lives in how the reader is built, which is why "cannot return anything outside that list" is the load-bearing phrase in the prompt, and why the verification step isn't optional.

The principle: make the scope structural, not a filter. Personal messages aren't filtered out of the results; they're in data the tool never opens. There's no filter to get wrong.

The payoff: the list is the permission. Add someone in Contacts and Claude can see that conversation; remove them and access is gone. No settings to edit, no list maintained in two places. The one hard rule: it never sends. Drafting is fine (it opens Messages with the reply loaded and you press send). Because no send capability exists in the code, it can't text anyone even if asked.

Already installed the starter kit? The full walkthrough ships in the kit's docs/ as the scoped iMessage access primer, including the traps a real build hit.

Not on a Mac? The texts part needs one: iMessage's database only exists on Apple devices. But the trick isn't Mac-only: the same work-contacts label can scope Claude's email or calendar reading instead. Same wording, same verification step.
